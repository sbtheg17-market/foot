Replit Task: Role-Aware Marketplace Signup and Onboarding
Objective
Implement a shared, intuitive authentication and onboarding flow for an eventual two-sided care marketplace. The experience must support both clients and providers without creating two unrelated authentication systems, while maximizing completed signup and first meaningful use.

The design must preserve existing booking, review, care-history, notification, authorization, and privacy behavior.

Current synchronized repository checkpoint: 7a730e3737543de0d3366570d9b439fc07861558.

Local and origin/main are synchronized at 0 / 0.

Working tree is clean.

Client-safe care history is implemented and verified.

Provider-private careNotes must remain unavailable in all client responses and UI.

Do not begin Stripe, admin, care-history expansion, or unrelated review work in this task.

Product principles
Use one shared authentication system and one account identity.

Treat the signup role selection as intent, not authorization.

Enforce roles and ownership on the server for every protected operation.

Keep client signup short and let clients reach marketplace value quickly.

Collect provider information progressively after account creation.

Do not force a user to create a second account to use another role later.

Preserve a path for an existing client to become a provider through an explicit “Become a provider” flow.

Do not require payment or payout onboarding during ordinary client signup.

Do not expose provider-private information to clients.

Prefer clear, friendly language over internal terms such as RBAC, connected accounts, or state machines.

Signup UX
Entry experience
Create a clear first step with two plain-language choices:

“I’m looking for care” — find a provider, request a booking, and manage appointments.

“I provide care” — offer services, manage availability, and receive bookings.

Use cards or large accessible buttons with short descriptions. Make the choice reversible before submission and provide a visible “Change role” action during onboarding.

Do not make users answer unnecessary questions before account creation. If a user arrives from a provider-specific call to action, preselect provider intent while still allowing them to change it.

Shared account form
Use one shared account form for both roles:

Email.

Password or the project’s existing authentication method.

Display name only if already required by the current product.

Terms and privacy acknowledgement where required.

Preserve existing email or phone verification, password recovery, session, and error behavior. Do not add a new authentication provider unless explicitly requested.

Conversion requirements
Optimize for completion without weakening security:

Keep the first screen focused on one decision.

Use one primary action per step.

Show a short progress indicator only for multi-step onboarding.

Preserve selected role and entered non-sensitive form values after validation errors.

Show field-level errors next to fields and a clear summary for screen readers.

Disable duplicate submission while the request is pending.

Make errors actionable and avoid clearing the entire form after a failure.

Avoid asking clients for provider-only information.

Let clients browse or reach their dashboard immediately after required verification and minimal profile completion.

Allow providers to save progress and return later if onboarding is multi-step.

Do not block account creation on optional profile fields.

Use responsive layouts that work at 390px.

Ensure keyboard navigation, labels, focus management, contrast, and touch targets meet existing project standards.

Do not use dark patterns, misleading defaults, hidden role changes, or unnecessary urgency.

Client flow
Implement or preserve this logical flow:

text
/signup?role=client
→ create shared account
→ verify email or phone if required
→ collect only basic client profile data
→ /client/dashboard or marketplace browse
Client onboarding should not ask for provider credentials, service offerings, availability, payout details, licensing, or compliance documents.

If a client later selects “Become a provider,” create an explicit provider-onboarding application for the same authenticated user. Do not create a second account.

Provider flow
Implement or preserve this logical flow:

text
/signup?role=provider
→ create shared account
→ verify email or phone if required
→ collect provider profile and service information
→ collect availability and required compliance details
→ pending review or approved provider state
→ /provider/application-status or /provider/dashboard
Separate required fields from optional fields. Allow safe progress saving if the existing architecture supports it. Do not integrate Stripe in this task; reserve payout onboarding for the later payment checkpoint.

Provider onboarding must not grant provider privileges merely because the user selected the provider option. The server must determine whether the provider profile is incomplete, pending, approved, rejected, or suspended.

Authorization model
Use the existing authorization system where possible. The conceptual model should support:

text
User
├── authentication identity
├── one or more roles
├── optional client profile
└── optional provider profile
Rules:

Role selection from the UI is never trusted as authorization.

The server derives the authenticated user from the session.

Every protected endpoint checks authentication, role, ownership, and provider approval state where applicable.

Clients can access only their own client data.

Providers can access only their authorized provider data.

Provider-private careNotes remain excluded from client responses, serializers, logs, and UI.

A user may have both roles only through an explicit, authorized flow.

Existing admin and provider-private permissions must not be broadened.

If the current schema cannot safely support a role-aware model, stop and report the constraint rather than making an unplanned migration.

Redirect logic
Redirect using server-confirmed role and onboarding state, not only a query parameter:

text
client + incomplete profile   → /onboarding/client
client + complete profile     → /client/dashboard
provider + incomplete profile → /onboarding/provider
provider + pending review     → /provider/application-status
provider + approved           → /provider/dashboard
Handle these cases safely:

Already-authenticated user opens signup.

User changes role before account creation.

User refreshes during onboarding.

User returns with an incomplete provider application.

User tries to access the other role’s protected route.

Email or phone verification is incomplete.

Signup request is submitted twice.

Email already exists.

Network failure occurs during signup.

Session expires during onboarding.

Do not redirect users into a privileged dashboard until the server confirms the required state.
