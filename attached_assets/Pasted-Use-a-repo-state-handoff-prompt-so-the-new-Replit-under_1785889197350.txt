Use a **repo-state handoff prompt** so the new Replit understands it is inheriting an in-progress build, not starting fresh. The key is to tell it the **current verified state**, the **latest constraints**, and the **next immediate task**.

## Paste this into the new Replit

```md
You are taking over an in-progress build of OnCall Foot from a previous Replit session.

Important: do not restart from scratch. You are inheriting the latest committed state from GitHub and should continue from there.

Known current state:
- API server is running and healthy.
- Auth routes work.
- DB schema is live.
- Seed data exists.
- TypeScript is clean.
- docs/commit-strategy.md exists and should be followed.
- The repo was built in fragments by previous agents, so you must inspect the whole repo before changing anything.

Current product direction:
- Provider-first marketplace
- /provider/* should be the canonical provider route group
- / should redirect to provider home for now
- client/admin portals are not in current build scope
- monetization UI is not in current build scope
- keep the backend/source-of-truth stable

What to continue from:
- the latest GitHub state from a few minutes ago
- the most recent committed checkpoint
- the current provider-first refactor and business-route expansion

Your first steps:
1. Inspect the full repository.
2. Identify what was already completed in the last session.
3. Report the current structure and what remains.
4. Continue only from the latest committed changes.
5. Do not rebuild working auth/schema/seed code.
6. Do not add client/admin UI.
7. Do not add monetization UI.
8. Keep changes checkpoint-sized and easy to push.

Workflow rules:
- preserve existing working backend behavior
- keep commits small
- push stable progress to GitHub frequently
- separate refactors from feature work whenever possible
- report broken references before changing them
- use centralized route constants and permissions
- if you find overlapping portal fragments, reconcile them into one coherent app

Before coding, tell me:
- what the repo currently contains
- what changed most recently
- what you will continue next
```

## Why this works

This tells the new Replit three crucial things:
- it is a **handoff**, not a new project,
- it should trust the **latest GitHub commit**,
- and it should continue with the same **provider-first scope and checkpoint discipline**.

## If you want stronger continuity

You can also add this line at the top:

```md
Treat GitHub as the source of truth and assume the latest pushed commit contains the most recent working state from the previous session.
```

That reduces the chance it tries to re-invent already-finished pieces.
