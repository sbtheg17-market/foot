Replit Phase 4 Handoff: Shared Signup and Role-Aware Onboarding
Phase placement
This phase begins only after Phase 3 authorization hardening is complete, verified, pushed, and synchronized with origin/main at 0 / 0.

Phase 3 must establish that:

authorization is based on server-side role membership;

provider operational access requires approved-provider state;

provider application ownership is enforced;

admin permissions remain isolated;

pending, rejected, and suspended providers cannot use approved-provider operations;

client and provider privacy boundaries remain intact;

JWT claims remain compatible or any changes are explicitly documented;

the full regression suite passes.

Do not begin this phase from an unsynchronized or partially verified Phase 3 state.

Objective
Implement a shared, intuitive signup and onboarding experience for the two-sided care marketplace:

One authentication system.

One account identity.

Clear client and provider intent.

Short client signup.

Progressive provider onboarding.

Server-confirmed redirects.

No duplicate accounts for users who later add a second role.

Strong authorization and privacy boundaries.

A low-friction path from landing page to first meaningful marketplace action.

The user experience should maximize completed signup and first use without weakening verification, authorization, or privacy.

Hard scope boundaries
In scope:

Shared signup entry point.

Client/provider intent choice.

Web and mobile signup experience.

Client onboarding state.

Provider application onboarding state.

Existing-user “Become a provider” entry point.

Server-confirmed onboarding redirects.

Form validation, loading, error recovery, accessibility, and responsive behavior.

Focused auth/onboarding tests.

Documentation and synchronized checkpoints.

Out of scope:

Stripe, payouts, connected accounts, or payment onboarding.

Provider approval policy redesign.

Admin workflow redesign.

New booking state transitions.

New review functionality.

Care-history expansion.

Provider-private careNotes changes.

Removing compatibility fields such as users.role.

Destructive schema cleanup.

New authentication providers unless separately approved.

Marketing experiments requiring a new analytics vendor.

Conversion-first UX strategy
The primary conversion goal is not merely account creation; it is getting a user to the first useful action quickly and safely.

Landing and entry points
Use clear role-specific calls to action:

“Find care” or “I’m looking for care.”

“Provide care” or “I provide care.”

Both should lead to the same signup system with role intent preselected. The user must be able to change their choice without restarting the flow.

Do not show provider-only requirements to a client before the client chooses provider intent.

Role choice
Present two accessible cards or large buttons with concise explanations:

“I’m looking for care” — Find a provider, request a booking, and manage appointments.

“I provide care” — Offer services, manage availability, and receive bookings.

Requirements:

One obvious primary action.

Clear selected state.

Keyboard and screen-reader support.

Touch targets safe for mobile.

No preselected provider role unless the user arrived from a provider-specific CTA.

Visible “Change role” action in later onboarding steps.

Role intent must never grant permissions.

Shared account creation
Use one shared form and existing authentication service.

Required only if already part of the current contract:

Email.

Password or existing authentication credential.

First name.

Last name.

Optional:

Phone.

Do not request provider services, availability, licensing, payout details, compliance documents, or business information in the shared account form.

Preserve existing authentication behavior, password rules, session creation, error format, and recovery behavior unless a change is required by the hardened authorization model.

Form behavior
Preserve non-sensitive entered values after validation errors.

Preserve role intent after network or validation failures.

Show field-level errors beside fields.

Include an accessible error summary.

Disable the submit action while the request is pending.

Prevent duplicate account creation requests.

Show a clear success/loading transition after account creation.

Do not clear the entire form after a transient network error.

Do not expose whether an email belongs to an account beyond the existing security policy.

Provide a clear path to login for existing users.

Ensure terms and privacy links are visible where required.

Client conversion path
Keep the client path minimal:

text
/signup?role=client
→ shared account creation
→ required verification if already supported
→ minimal client state
→ /discover or /client/dashboard
→ browse providers or request a booking
Do not block browsing on optional client profile fields. Do not ask for provider-only information. If the marketplace requires a minimal client profile, explain why each required field is needed and keep the number of steps small.

Provider conversion path
Keep account creation simple, then use progressive onboarding:

text
/signup?role=provider
→ shared account creation
→ required verification if already supported
→ /onboarding/provider
→ save provider application draft
→ submit application
→ /provider/application-status
→ /provider after approval
Provider onboarding should clearly show:

Current step.

Completed steps.

Remaining required information.

Whether data is saved.

What happens after submission.

Expected application status.

Allow providers to save progress and return later. Do not ask for Stripe or payout information in this phase.

Recommended provider steps:

Basic provider identity and public title.

Bio and experience.

City and service area.

Services offered.

Availability.

Required verification metadata.

Review and submit.

Use the existing provider application APIs and authorization rules. Do not create a second provider account or duplicate application.

Existing-user role expansion
Add a clear “Become a provider” action for authenticated clients only after Phase 3 authorization is available.

Required behavior:

Reuse the existing authenticated user.

Confirm the user’s session server-side.

Check whether a provider role already exists.

Return the existing provider application if one exists.

Otherwise create provider role membership and draft application transactionally.

Preserve existing client role and client access.

Do not grant provider operational access before approval.

Make repeated requests idempotent.

Redirect to provider onboarding or the existing application status.

Do not silently change a user’s active role or remove their client capabilities.

Server-confirmed redirect logic
Use GET /auth/me or the project’s server-confirmed account-state endpoint as the redirect source.

Expected behavior:

text
Unauthenticated user                 → /login or /signup
Client role, incomplete state        → /onboarding/client
Client role, complete state          → /discover or /client/dashboard
Provider application draft           → /onboarding/provider
Provider application under_review    → /provider/application-status
Provider application approved       → /provider
Provider application rejected        → /provider/application-status with resubmit path
Provider application suspended       → /provider/application-status with support path
Admin                                → existing admin route
Rules:

Do not trust ?role=provider for access.

Do not route to provider operations until Phase 3 approved-provider checks pass.

Refresh account state on initial app load and after onboarding mutations.

Handle refresh, browser back, app resume, and expired sessions safely.

Preserve a provider’s draft step on return.

Redirect expired sessions to login without losing safe local navigation context.

Authorization and privacy requirements
Client-controlled role intent is never authorization.

Server role membership determines available role contexts.

Approved-provider middleware remains the authority for provider operations.

Provider application endpoints may be accessible to the authenticated owner during onboarding, but must enforce ownership.

Admin endpoints remain admin-only.

Client endpoints remain scoped to the authenticated client.

Provider-private careNotes must remain absent from all client API responses, logs, serialized objects, and UI.

Existing bookings, reviews, care history, notifications, and provider data boundaries must not regress.

API behavior
Reuse the current API contracts wherever possible.

If signup needs a role-intent field, use a clearly named field such as roleIntent rather than treating role as authorization. Maintain backward compatibility for the existing registration field during the transition if required.

Provider onboarding should use authenticated, ownership-scoped endpoints such as:

text
GET /providers/application
POST /providers/application
PATCH /providers/application
POST /providers/application/submit
Use the actual project routes if different. Do not invent duplicate endpoints when existing Phase 2/3 APIs provide the required behavior.

All new or changed endpoints must:

Validate input server-side.

Enforce session ownership.

Return stable error shapes.

Be documented in OpenAPI when the contract changes.

Regenerate clients using the official codegen command.

Avoid exposing private reviewer notes or verification details.

Stop conditions
Stop and request review if:

Signup requires a new schema migration not covered by Phase 0/1/2.

Authorization behavior is ambiguous.

A client-controlled value could grant provider access.

Existing users would need duplicate accounts.

Provider-private data could be exposed.

A payment or payout requirement appears.

Existing booking, review, care-history, or notification behavior regresses.

A force-push or history rewrite appears necessary.

The remote branch diverges unexpectedly.

Usage limits may prevent a complete checkpoint.
