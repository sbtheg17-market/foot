Step 2: idempotent account-role backfill
Backfill exactly one role membership from each existing users.role value:

text
users.role = client   → account_roles(user_id, client)
users.role = provider → account_roles(user_id, provider)
users.role = admin    → account_roles(user_id, admin)
Requirements:

Use a transaction where supported.

Use the unique (user_id, role) constraint.

Use conflict-safe insertion such as ON CONFLICT DO NOTHING or the project’s equivalent.

Make the operation safe to run repeatedly.

Never delete existing valid role memberships.

Never add secondary roles automatically.

Never update users.role as a side effect.

Never grant provider or admin access beyond the existing persisted role.

Return a summary of inserted, already-present, skipped, and failed records.

The second execution must produce no additional inserts and no changed rows.

Step 3: provider-application backfill
Create one provider application for each existing provider profile or provider user according to the approved mapping.

Recommended mapping:

text
approved      → approved
under_review  → under_review
rejected      → rejected
pending with submitted verification material → under_review
pending without submitted verification material → draft
provider user without profile → draft, with incomplete provider profile
Requirements:

Use the existing provider profile as the linked provider profile.

Preserve existing provider profile data.

Preserve the existing verificationStatus field.

Use provider_applications.status as the new compatibility representation for migration purposes, but do not make it the sole authorization source in this phase.

Do not mark an incomplete provider as approved.

Do not create duplicate applications.

Use the unique user and provider-profile constraints.

Make the backfill idempotent.

Do not create provider applications for client-only or admin-only users.

Do not automatically create client memberships for providers.

Do not send notifications or emails as a backfill side effect.

For every backfilled provider application, preserve:

User ownership.

Provider profile ownership.

Existing verification state.

Existing review or verification metadata where a safe mapping exists.

Created and updated timestamps according to project conventions.

If the existing schema cannot safely determine whether a pending provider submitted verification material, use the safer draft state and document the limitation rather than granting operational access.

Step 4: compatibility invariants

Required invariants:

Step 5: additive server-state exposure
Expose server-confirmed role and onboarding data through existing authenticated account responses without changing authorization behavior.

GET /auth/me
Add fields additively where compatible:

json
{
  "user": {
    "id": 1,
    "email": "client@example.test",
    "role": "client",
    "roles": ["client"],
    "activeRole": "client",
    "onboarding": {
      "client": "complete",
      "provider": null
    },
    "providerApplication": null
  }
}
For a provider:

json
{
  "user": {
    "id": 2,
    "email": "provider@example.test",
    "role": "provider",
    "roles": ["provider"],
    "activeRole": "provider",
    "onboarding": {
      "client": null,
      "provider": "approved"
    },
    "providerApplication": {
      "status": "approved",
      "currentStep": null
    }
  }
}
For a user with both memberships, if such a record exists in a test fixture or controlled migration test:

json
{
  "roles": ["client", "provider"],
  "activeRole": "client",
  "onboarding": {
    "client": "complete",
    "provider": "under_review"
  }
}
Rules:

role remains the legacy scalar compatibility field.

roles is derived from account_roles, not from client input.

activeRole remains the current legacy context unless the existing session model already supports safe context selection.

Do not add an active-role mutation endpoint in Phase 2.

providerApplication is returned only for the authenticated owner or an authorized admin.

Do not expose reviewer notes or private verification details to ordinary clients.

Do not expose provider-private careNotes.

Keep response shapes backward-compatible for current web and mobile clients.

If the API uses a different response envelope, follow the existing convention rather than forcing this exact shape.

JWT behavior
Keep JWT issuance and claims unchanged in Phase 2:

json
{
  "sub": 1,
  "email": "user@example.test",
  "role": "client"
}
Do not put the full role array or provider approval state into the token yet. The database-backed response is the source of newly exposed server state. This avoids stale authorization claims while the compatibility phase is in progress.
