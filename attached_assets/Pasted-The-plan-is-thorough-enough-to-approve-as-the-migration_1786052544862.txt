The migration plan is approved for staged implementation, subject to these constraints.

Do not implement the entire migration as one large change.
Do not remove users.role yet.
Do not change or break existing client, provider, admin, booking, review, care-history, or notification behavior.
Do not add Stripe, payouts, connected accounts, or payment onboarding.
Do not require existing users to create new accounts.
Do not automatically grant clients provider roles.
Do not grant provider privileges from role intent or a client-controlled request.

Required implementation phases:

Phase 0 — Planning artifacts only
- Preserve the approved migration plan.
- Add the migration plan to the appropriate project documentation.
- Record open decisions, assumptions, rollback strategy, and data preflight checks.
- No runtime behavior changes in this phase.

Phase 1 — Additive database migration
- Add account_roles.
- Add provider_applications.
- Add provider_application_events only if the existing project’s audit requirements justify it.
- Keep users.role unchanged.
- Add foreign keys, unique constraints, and indexes.
- Make the migration idempotent and reversible where practical.
- Run a preflight report before backfilling.
- Fail safely on orphaned, duplicate, null, or inconsistent data.
- Never map invalid data to admin or provider access.

Phase 2 — Backfill and compatibility
- Backfill one matching account_roles record from each current users.role.
- Do not add secondary roles automatically.
- Backfill provider applications from existing provider profile status.
- Preserve approved existing providers without forcing re-onboarding.
- Keep users.role and the scalar API role field temporarily.
- Add roles, activeRole, onboarding, and providerApplication as additive response fields.
- Add consistency checks between users.role and account_roles.
- Do not allow client input to directly mutate users.role.

Phase 3 — Authorization hardening
- Treat the JWT as user identity, not as the complete authorization source.
- Add server-side role membership checks.
- Add approved-provider checks for operational provider routes.
- Require authenticated ownership for provider onboarding endpoints.
- Preserve admin-only authorization.
- Ensure provider-private careNotes remain absent from client responses, serializers, logs, and UI.
- Add regression tests before changing frontend behavior.

Phase 4 — Shared signup and onboarding
- Add /signup as the shared entry point.
- Keep /register as a compatibility redirect.
- Support client and provider intent without treating intent as authorization.
- Keep client signup minimal.
- Create provider application draft state only through a server-authorized flow.
- Add /onboarding/client, /onboarding/provider, and /provider/application-status only if they match the existing routing architecture.
- Use GET /auth/me as the source for redirect decisions.
- Preserve form values after validation and network failures.
- Prevent duplicate signup and duplicate provider-application submissions.
- Do not require Stripe or payout information.

Phase 5 — Existing-user and dual-role flow
- Add “Become a provider” for an authenticated client.
- Reuse the existing user account.
- Add provider role membership transactionally.
- Create or return the existing provider application.
- Keep client access intact.
- Do not grant provider operational access until approval.
- Make repeated requests idempotent.
- Add tests for client-only, provider-only, dual-role, admin-only, pending, rejected, and suspended states.

Phase 6 — Cleanup only after evidence
Do not remove users.role or old provider status fields until:
- all consumers use account_roles and provider_applications;
- compatibility behavior has been observed successfully;
- migrations have been tested on realistic data;
- rollback has been validated;
- production synchronization and monitoring are available;
- a separate cleanup checkpoint is explicitly approved.

Required product decisions to leave documented:
- Whether a user may actively switch between client and provider contexts.
- Whether provider role addition requires admin review before application creation.
- Which provider fields are required before application submission.
- Whether rejected providers may resubmit and under what conditions.
- Whether an approved provider may also book as a client.
- Whether the client dashboard should be /discover or /client/dashboard.
- Whether email or phone verification is required before booking or provider application submission.

Checkpoint rules:
- Commit each phase separately.
- Run focused tests before each commit.
- Run full typecheck, build, booking, review, care-history, concurrency, and new auth/onboarding tests before the final checkpoint.
- Update OpenAPI and generated code only after API contracts are settled.
- Never edit generated files manually.
- Push each stable checkpoint normally to origin/main.
- Confirm local and remote hashes match and ahead/behind is 0/0 after every pushed checkpoint.
- Stop immediately if GitHub authentication fails, data preflight fails, tests regress, or usage limits may prevent a complete checkpoint.

Start with Phase 0 and Phase 1 only. Do not modify signup UI or runtime authorization until the additive schema design, data preflight checks, and migration rollback plan are reviewed.
Why this sequence is safest
It separates data structure, authorization, and user experience. That prevents the common failure where the interface offers “provider” signup before the backend can safely distinguish provider intent, provider application status, and approved provider privileges.

The current booking, reviews, care-history, and notification checkpoints should remain untouched while Phase 1 is implemented.
